# Proposal requirements and acceptance evidence

Reviewed 20 October 2026 against the SPAP proposal and subsequent project decisions. The backend/database phase is separate from the frontend and genuine ML phase. An interface is not evidence that a model has been implemented. The application runs locally; the previously approved Supabase service provides database and identity. No new hosting is introduced.

| Requirement | Backend/database implementation | Acceptance and remaining boundary |
|---|---|---|
| FR1 — transaction ingestion | Validated integer money, currency, UTC timestamps, channel, source/destination accounts, merchant/device/location context; single and atomic 100-item batches | Real Supabase tests verify conflicting retries, overlapping batches, ordering, atomic failure and exactly one job/audit per accepted transaction. Optional context supports the proposal fields; upstream data quality remains the producer's responsibility. |
| FR2 — rolling account features | Immutable versioned 1h/24h/7d feature snapshots, currency separation, cold-start and late-event policy | Tests cover historical evidence boundaries and feature snapshots. Supabase replaces the proposal's in-memory state under the user's database decision; measured latency is recorded rather than assumed. |
| FR3 — calibrated supervised probability | Approved-model registry, fixed authenticated HTTPS adapter, bounded validated probability contract | Genuine supervised training, calibration and evaluation remain the ML phase. Disabled scoring cannot report a normal verdict. |
| FR4 — independent anomaly score | Separate anomaly value in the provider contract and persisted evidence | Genuine anomaly-model training and evaluation remain the ML phase. |
| FR5 — fused score, severity and review capacity | Risk-score contract, independent approval of policy versions; review-capacity and configurable severity implemented in revision 0008 | Revision 0008 is applied to both schemas. A capacity target never discards alerts. Actual score fusion/calibration and tuning to capacity require the ML dataset and evaluation. |
| FR6 — five contributors | Remote adapter requires five bounded explanation contributions, with direction/magnitude; immutable result | Contract tests pass. Actual explanation fidelity and model feature attribution require the ML phase. |
| FR7 — review queue and history | Scoped/filterable risk-ranked cases, history, assignment, summaries, notes, evidence and investigation lifecycle | Integration tests cover team/assignment isolation, deterministic pagination and history boundaries. Frontend presentation remains separate. |
| FR8 — reviewer decisions | Immutable attributed decisions; independent approval for simulated protective actions; recent MFA; durable execution receipts | Tests exercise cancellation, approval/worker races, retry, evidence changes, dual control and audit atomicity. Real Supabase users/MFA are still required for a real-user demonstration. |
| FR9 — retraining and versioning | Hashed immutable reviewed-label snapshots, training handoff lifecycle, versioned approved models | Export/governance implemented. Actual training, model evaluation and reproducible training artifacts remain the ML phase. |
| FR10 — threshold and performance management | Approved versioned policies; private health/queue/error/latency monitoring with six alerts | Local HTTPS and alert lifecycle checked. Revised final monitoring build must pass its final acceptance. Model-quality reports require actual model evaluation. |
| FR11 — drift | Governed drift-report storage/read interface | Actual reference/current-distribution comparison and drift calculation remain the ML phase. Stored reports are not a drift detector. |
| NFR1 — scoring p95 ≤200 ms | Bounded ingestion, durable asynchronous worker, provider deadline | Not met. Real-Supabase baseline acceptance p95 was 2.89–4.16 seconds and is not scoring latency. No genuine-model end-to-end latency claim. |
| NFR2 — ≥100 TPS on four cores | Concurrent bounded API and workers; bulk ingestion | Not met. New 100-item batch accepted in 5.77 seconds (17.35 items/s in one batch); this is neither sustained throughput nor scoring throughput. Proposal permits honestly reported micro-batching as fallback. |
| NFR3 — synthetic/public data, encryption | Synthetic-only workflow, verified database TLS, local TLS, least privilege, protected secrets, non-public app tables | Managed storage/disk encryption and organizational data-handling controls require deployment evidence. Singapore Supabase location does not establish Saudi residency compliance. |
| NFR4 — reproducibility | Locked Python dependencies, pinned image/source inputs, explicit migrations, immutable features/results/snapshots | Actual model seeds, training data splits and model artifacts belong to ML acceptance. |
| NFR5 — usable dashboard | Scoped frontend-ready APIs and local operational health page | Analyst/customer frontend and usability assessment remain separate. |
| NFR6 — single-command startup | `backend/.venv/bin/python backend/scripts/demo.py start` | Requires Docker, prepared restricted Supabase credentials, network, and a sufficiently current local certificate. Initial dependency builds are slower. |
| NFR7 — attribution | Attribution register, upstream licenses retained in images, recorded sources | See `ATTRIBUTION.md`; public datasets/model artifacts must add their licenses when introduced. |
| Retained phone feature | Participant-bound EN/AR simulated calls, protected offline introductory audio, transcripts and structured responses | Both language workflows tested. Neither a real phone call nor unrestricted AI bank agent is claimed. |
| Security mapping | Access controls, MFA/session/CSRF, immutable audit/evidence, transactional workflows, incident/recovery procedures | ASVS/NCA/SAMA mapping is engineering evidence, not certification; see security review and status register. |

## Evidence interpretation

The completed 17 October full run passed 122 checks. One subsequently added configuration-redaction check passed in a six-test targeted local-operations run. On 20 October, all five batch/regression tests passed. These reports are separate runs; their counts must not be added blindly because some tests overlap. Raw JUnit files are under `backend/test-results-*.xml`.

The workload report in `evidence/local-performance.json` preserves the baseline rather than replacing it with health-endpoint throughput. `evidence/batch-performance.json` records the new bounded ingestion measurement. `evidence/local-acceptance.json` records live gateway/access/isolation checks. A security scanner finding no known vulnerabilities does not prove absence of vulnerabilities.
